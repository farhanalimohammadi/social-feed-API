# ۱۲ - راهنمای ارائه‌ی پروژه در مصاحبه‌ی فنی

این راهنما کمک می‌کند پروژه را دقیق، روان و بدون اغراق توضیح دهید. هر ادعایی که اینجا آمده در کد فعلی وجود دارد. محدودیت‌ها هم صادقانه ذکر شده‌اند، چون مصاحبه‌کننده‌ی فنی معمولاً صداقت درباره‌ی trade-offها را بیشتر از فهرست بلند قابلیت‌ها ارزش‌گذاری می‌کند.

---

## توضیح ۳۰ ثانیه‌ای

> «Social Feed API یک REST API با NestJS و TypeScript است که هسته‌ی یک شبکه‌ی اجتماعی را پیاده می‌کند: ثبت‌نام و ورود با JWT، ساخت پست، کامنت و پاسخ، فید عمومی صفحه‌بندی‌شده و پروفایل کاربر. PostgreSQL منبع حقیقت است و یکپارچگی داده را با constraintهای خود پایگاه داده تضمین می‌کنم. Redis فقط برای cache فید و rate limit ساخت پست است و اگر از دسترس خارج شود، سیستم همچنان کار می‌کند. پروژه سه لایه تست دارد: Unit، Integration روی پایگاه داده و Redis واقعی، و E2E.»

---

## توضیح ۲ دقیقه‌ای معماری

> «ساختار پروژه feature-based است. هر دامنه یعنی auth، posts، comments، users، rate-limit و health یک ماژول NestJS جداگانه دارد. Controllerها نازک‌اند و فقط ورودی را به Service می‌دهند. منطق کسب‌وکار در Serviceهاست.
>
> برای دسترسی به داده لایه‌ی Repository نگذاشتم، چون Prisma خودش API تایپ‌شده دارد. به‌جایش برای هر query یک شیء select نام‌دار تعریف کرده‌ام و نوع ردیف را از همان select مشتق می‌کنم. بعد یک mapper آن را به شکل پاسخ API تبدیل می‌کند. نتیجه این است که مثلاً `passwordHash` فقط در یک نقطه، یعنی login، صریحاً خوانده می‌شود و ایمیل در هیچ پاسخ عمومی‌ای نیست.
>
> PrismaService و RedisService تنها مرز ارتباط با زیرساخت‌اند و هر دو global هستند. RedisService همه‌ی خطاها را می‌گیرد و null برمی‌گرداند. به همین دلیل خرابی Redis هیچ‌وقت به خطای HTTP تبدیل نمی‌شود.
>
> فید با الگوی cache-aside در Redis cache می‌شود. invalidation با یک شمارنده‌ی generation انجام می‌شود که در کلید هر صفحه وجود دارد. با هر پست یا کامنت جدید فقط یک INCR می‌زنم. rate limit ساخت پست یک fixed window به ازای کاربر است که با یک اسکریپت Lua اتمیک پیاده شده و در زمان خرابی Redis، fail-open رفتار می‌کند.
>
> در پایگاه داده، مهم‌ترین نکته یک foreign key مرکب روی `(parent_comment_id, post_id)` است. این کلید تضمین می‌کند پاسخ هر کامنت حتماً در همان پست باشد. CHECK constraintها هم جلوی متن خالی و شناسه‌های غیر lowercase را می‌گیرند.»

## توضیح فنی مفصل

### جریان درخواست

`helmet` و CORS شرطی ← مسیر `/api/v1` ← Guardها (`JwtAuthGuard` و در ساخت پست، `PostCreateRateLimitGuard`) ← `ValidationPipe` سراسری با `whitelist` و `forbidNonWhitelisted` ← Controller ← Service ← Prisma یا Redis ← mapper ← JSON. هر خطا از `AllExceptionsFilter` عبور می‌کند. قالب خطا واحد است و پیام خطاهای ۵xx پنهان می‌شود.

### احراز هویت

- ورود: `bcrypt.compare` همیشه اجرا می‌شود. اگر ایمیل وجود نداشته باشد، روی یک dummy hash. پیام خطا در هر دو حالت `Invalid credentials` است.
- توکن: payload فقط `{ sub }` است. verify فقط `HS256` را می‌پذیرد و انقضا را بررسی می‌کند.
- `JwtStrategy.validate`: بررسی می‌کند که `sub` یک UUID نسخه‌ی ۴ باشد و کاربر را از پایگاه داده می‌خواند. کاربر حذف‌شده فوراً `401` می‌گیرد.
- رمز عبور با طول بایتی ۸ تا ۷۲ محدود شده، چون bcrypt فقط ۷۲ بایت اول را در نظر می‌گیرد.

### Cache فید

- کلیدها: `posts:feed:v1:generation` و `posts:feed:v1:g{gen}:page:{p}:limit:{l}`.
- در MISS، نتیجه زیر **همان** generation که در ابتدای درخواست خوانده شده ذخیره می‌شود. اگر هم‌زمان invalidation رخ دهد، داده‌ی کهنه زیر کلیدی نوشته می‌شود که دیگر کسی آن را نمی‌خواند.
- payload همان DTO نهایی است. هنگام خواندن، codec شکل داده را بررسی و Dateها را بازسازی می‌کند. اگر داده خراب باشد، کلید حذف و درخواست مثل MISS از پایگاه داده پاسخ داده می‌شود.

### Rate limit

- کلید: `ratelimit:posts:create:v1:user:{userId}:window:{index}`.
- Lua: `INCR` و فقط در اولین افزایش، `EXPIRE`، به‌صورت اتمیک.
- تست Integration: ۲۵ فراخوانی موازی روی Redis واقعی دقیقاً ۱۰ پذیرش می‌دهد.

### پایگاه داده

- FK مرکب و `@@unique([id, postId])` لازمه‌ی آن.
- `CHECK`ها در migration دستی دوم.
- indexهای مرکب `(…, created_at DESC, id DESC)` به‌همراه دو index جزئی برای کامنت‌های سطح اول و پاسخ‌ها.
- `ON DELETE RESTRICT` در همه‌ی روابط.

## اگر از من بپرسند چرا...

### چرا NestJS؟
DI داخلی، ماژول‌بندی صریح و مفاهیم استاندارد Guard، Pipe و Filter. این‌ها اجازه می‌دهند مسئولیت‌های cross-cutting مثل احراز هویت، validation و قالب خطا یک بار و یک‌جا تعریف شوند. تست‌پذیری هم با `@nestjs/testing` ساده است.

### چرا PostgreSQL؟
داده رابطه‌ای است و قواعدی دارد که می‌خواستم در خود پایگاه داده اجرا شوند: unique، FK مرکب و CHECK. PostgreSQL همه‌ی این‌ها را به‌همراه index جزئی دارد.

### چرا Prisma؟
API تایپ‌شده، migrationهای مدیریت‌شده و مهم‌تر از همه، اینکه نوع ردیف از شیء select مشتق می‌شود. اگر فیلدی را از select حذف کنم، mapper در زمان کامپایل خطا می‌دهد. محدودیتش این است که CHECK و index جزئی را باید با SQL دستی اضافه کرد.

### چرا Redis؟
برای دو نیاز که به وضعیت مشترک بین instanceها و عملیات اتمیک سریع نیاز دارند: cache فید و شمارنده‌ی rate limit. cache در حافظه‌ی process بین چند instance ناسازگار می‌شد.

### چرا cache-aside؟
ساده‌ترین الگویی است که Redis را اختیاری نگه می‌دارد. اگر Redis نباشد، مسیر MISS همان مسیر عادی پایگاه داده است. در write-through نوشتن به Redis وابسته می‌شد.

### چرا invalidation با generation؟
یک پست جدید همه‌ی صفحات فید را جابه‌جا می‌کند. حذف تک‌تک کلیدها به `KEYS` نیاز داشت که مسدودکننده است، یا به `SCAN` که چندمرحله‌ای است. با generation فقط یک `INCR` اتمیک لازم است و کلیدهای قدیمی با TTL خودشان منقضی می‌شوند.

### چرا Lua؟
برای اینکه `INCR` و `EXPIRE` اتمیک باشند. اگر جدا اجرا می‌شدند، crash بین آن دو یک کلید بدون TTL باقی می‌گذاشت که کاربر را برای همیشه مسدود می‌کرد. همچنین یک round-trip به‌جای دو.

### چرا fixed window؟
ساده، O(1) و با یک کلید. ضعفش را می‌دانم: در مرز دو پنجره تا دو برابر سقف مجاز است. برای جلوگیری از اسپم ساخت پست این trade-off قابل قبول بود. sliding window را پیاده نکرده‌ام.

### چرا fail-open؟
چون Redis زیرساخت جانبی است. اگر fail-closed بود، خرابی Redis ساخت پست را برای همه از کار می‌انداخت. هزینه‌اش این است که در آن بازه حفاظت ضداسپم نداریم. برای اینکه کلاینت را گمراه نکنم، در حالت degraded هدر rate limit هم نمی‌فرستم.

### چرا فقط access token؟
محدوده‌ی پروژه را کوچک و قابل دفاع نگه داشتم. می‌دانم که logout و لغو توکن ندارم و توکن تا زمان انقضا معتبر است. قدم بعدی refresh token با چرخش است.

### چرا جست‌وجوی کاربر در `JwtStrategy`؟
تا کاربر حذف‌شده فوراً دسترسی‌اش را از دست بدهد و `request.user` داده‌ی تازه داشته باشد. هزینه‌اش یک query با کلید اصلی در هر درخواست محافظت‌شده است.

### چرا select صریح؟
تا هیچ فیلد حساسی تصادفی از پایگاه داده خارج نشود. `passwordHash` فقط در login خوانده و فوراً حذف می‌شود. Unit Test هم این را بررسی می‌کند.

### چرا FK مرکب؟
FK ساده فقط وجود والد را تضمین می‌کند، نه اینکه والد در همان پست باشد. با `(parent_comment_id, post_id) → (id, post_id)`، پایگاه داده خودش پاسخ بین‌پستی را رد می‌کند. Service هم پیش از آن بررسی می‌کند تا پیام `400` خوانا برگرداند، و تست Integration نشان می‌دهد که قید پایگاه داده مستقل از Service کار می‌کند.

### چرا offset pagination؟
کلاینت شماره‌ی صفحه و تعداد کل می‌خواهد و cache به ازای هر صفحه هم با آن ساده است. محدودیت‌هایش را می‌دانم: هزینه‌ی OFFSET در صفحات عمیق و جابه‌جایی آیتم‌ها هنگام درج. indexها با ترتیب `(created_at DESC, id DESC)` ساخته شده‌اند، پس مهاجرت به cursor از نظر index آماده است.

### چرا endpointهای جدا برای تاریخچه‌ی کاربر؟
صفحه‌بندی روی اجتماع پست‌ها و کامنت‌ها پیچیده است. پروفایل فقط ۵ مورد جدید ترکیبی را با هزینه‌ی ثابت نشان می‌دهد و تاریخچه‌ی کامل در `/users/:id/posts` و `/users/:id/comments` با صفحه‌بندی ساده و index مخصوص هر کدام ارائه می‌شود.

### چرا سه لایه تست؟
چون هر لایه چیزی را اثبات می‌کند که بقیه نمی‌توانند. Unit تصمیم‌های منطقی را سریع و بدون Docker می‌آزماید. Integration ثابت می‌کند FK مرکب و اسکریپت Lua روی زیرساخت واقعی درست کار می‌کنند. E2E ثابت می‌کند Guard، Pipe و فیلتر واقعاً همان‌طور سیم‌کشی شده‌اند که در production اجرا می‌شوند، چون از همان `configureApp` استفاده می‌کند.

## قوی‌ترین جنبه‌های مهندسی پروژه

1. **یکپارچگی در سطح پایگاه داده:** FK مرکب، CHECKها و RESTRICT، همراه با تست Integration که مستقیم روی PostgreSQL اجرا می‌شود.
2. **رفتار سنجیده در خرابی:** Redis با timeoutهای کوتاه و بدون صف آفلاین، و تبدیل خطا به `null`. فید و ساخت پست بدون Redis کار می‌کنند.
3. **invalidation بدون race:** نوشتن زیر generation خوانده‌شده.
4. **rate limit اتمیک با اثبات تجربی:** تست ۲۵ درخواست موازی.
5. **کنترل خروجی:** select صریح، نوع مشتق‌شده از select، mapper و codec اعتبارسنج برای داده‌ی cache.
6. **امنیت ورودی:** `forbidNonWhitelisted`، نرمال‌سازی در DTO و در پایگاه داده، `ParseUUIDPipe`، و گرفتن `authorId` از JWT.
7. **پیکربندی fail-fast:** متغیرهای محیطی نامعتبر مانع بالا آمدن برنامه می‌شوند.
8. **E2E هم‌سان با production:** استفاده از همان `configureApp`.
9. **CI کامل:** format، lint، typecheck، validate، سه لایه تست و build روی سرویس‌های واقعی.

| rate limit | فقط ساخت پست محدود شده است. login، register و کامنت محدودیت ندارند. انفجار در مرز پنجره ممکن است. درخواست‌هایی که در validation رد شوند هم سهمیه مصرف می‌کنند. |

## پرسش‌های فنی محتمل و پاسخ کوتاه

**اگر دو درخواست هم‌زمان با یک ایمیل ثبت‌نام کنند چه می‌شود؟**
قید `UNIQUE` پایگاه داده فقط یکی را می‌پذیرد. دومی خطای `P2002` می‌گیرد که `AuthService` آن را به `409` تبدیل می‌کند. پیش از insert بررسی جداگانه‌ای وجود ندارد، پس race ایجاد نمی‌شود.

**اگر Redis وسط کار قطع شود؟**
فرمان‌ها حداکثر پس از یک ثانیه شکست می‌خورند، یا فوراً اگر اتصال قطع باشد، چون صف آفلاین غیرفعال است. فید از پایگاه داده خوانده می‌شود و rate limit درخواست را می‌پذیرد. پس از اتصال مجدد، ioredis رویداد `ready` را می‌فرستد.

**چرا totalComments پاسخ‌ها را هم می‌شمارد؟**
چون از `_count.comments` روی رابطه‌ی پست می‌آید که همه‌ی کامنت‌های آن پست را شامل می‌شود. `totalReplies` روی هر کامنت فقط فرزندان مستقیم را می‌شمارد.

**کهنگی فید حداکثر چقدر است؟**
در حالت عادی فقط فاصله‌ی کوتاه بین commit و `INCR`. اگر `INCR` شکست بخورد، تا `FEED_CACHE_TTL_SECONDS` (پیش‌فرض ۳۰ ثانیه).

**آیا کاربر می‌تواند با فرستادن `authorId` به نام دیگری پست بگذارد؟**
خیر. `authorId` در DTO وجود ندارد، پس `forbidNonWhitelisted` درخواست را با `400` رد می‌کند (E2E این را تست کرده است). شناسه همیشه از JWT می‌آید.

**چرا `id` در مرتب‌سازی آمده است؟**
برای ترتیب قطعی. `created_at` دقت میلی‌ثانیه دارد و ممکن است تکراری باشد. بدون tie-breaker یکتا، صفحه‌بندی offset ممکن است ردیف تکراری یا جاافتاده داشته باشد.

**اگر پنجره ۶۰ ثانیه باشد و کاربر در ثانیه‌ی ۵۹ سقف را پر کند؟**
`Retry-After` برابر ۱ است و در ثانیه‌ی صفر پنجره‌ی بعدی می‌تواند دوباره تا سقف پست بگذارد. این همان trade-off پنجره‌ی ثابت است.

**چطور مطمئن هستید cache خراب برنامه را از کار نمی‌اندازد؟**
`parseFeedPage` هر فیلد را بررسی و Dateها را اعتبارسنجی می‌کند و در صورت هر ناسازگاری `null` برمی‌گرداند. کلید خراب حذف می‌شود و درخواست از پایگاه داده پاسخ داده می‌شود. Unit Test چهار حالت خراب را پوشش می‌دهد.

**مقیاس‌پذیری افقی چطور است؟**
برنامه stateless است: JWT دارد و session ندارد. cache و شمارنده‌های rate limit در Redis مشترک‌اند، پس چند instance رفتار سازگاری خواهند داشت. با این حال، استقرار چند instance در این مخزن پیکربندی یا تست نشده است.

## توضیح کامل پروژه به زبان گفتاری

> «این پروژه یک API برای یک شبکه‌ی اجتماعی ساده است. با NestJS و TypeScript نوشتمش، داده‌ها در PostgreSQL هستند و از Prisma استفاده کردم، و Redis هم دارد.
>
> کاربر ثبت‌نام می‌کند. رمزش با bcrypt هش می‌شود و برای ورود یک JWT می‌گیرد. موقع ورود حتی اگر ایمیل وجود نداشته باشد، مقایسه‌ی bcrypt را روی یک هش ساختگی انجام می‌دهم تا از روی زمان پاسخ یا پیام خطا نشود فهمید ایمیلی ثبت شده یا نه. در هر درخواست محافظت‌شده هم کاربر را از پایگاه داده می‌خوانم تا اگر حذف شده باشد، توکنش عملاً بی‌اثر شود.
>
> بعد کاربر پست می‌گذارد، زیر پست‌ها کامنت می‌گذارد و به کامنت‌ها پاسخ می‌دهد. یک نکته‌ای که رویش وقت گذاشتم این بود که پاسخ یک کامنت حتماً در همان پست باشد. این را هم در کد چک می‌کنم و هم با یک foreign key مرکب در خود پایگاه داده، تا حتی اگر کد اشتباه کند، داده خراب نشود. CHECK constraint هم گذاشتم که متن خالی یا ایمیل با حروف بزرگ وارد پایگاه داده نشود.
>
> فید عمومی پرمصرف‌ترین بخش است، برای همین در Redis cache می‌شود. برای باطل کردن cache به‌جای پیدا کردن و پاک کردن کلیدها، یک شماره‌ی نسخه دارم که در کلید هر صفحه وجود دارد. با هر پست یا کامنت جدید فقط آن شماره را یکی زیاد می‌کنم. برای جلوگیری از اسپم هم ساخت پست برای هر کاربر در هر پنجره‌ی زمانی محدود است. این را با یک اسکریپت Lua پیاده کردم که شمارش و تنظیم زمان انقضا را اتمیک انجام بدهد. یک تست هم دارم که ۲۵ درخواست هم‌زمان می‌فرستد و ثابت می‌کند دقیقاً ۱۰ تا پذیرفته می‌شوند.
>
> یک تصمیم مهم این بود که Redis نباید نقطه‌ی شکست باشد. اگر Redis قطع شود، فید از پایگاه داده خوانده می‌شود و rate limit درخواست‌ها را رد نمی‌کند. یعنی دسترس‌پذیری را به سخت‌گیری ترجیح دادم و می‌دانم که در آن بازه حفاظت ضداسپم نداریم.
>
> برای تست، سه لایه دارم. Unit Test برای منطق، Integration روی PostgreSQL و Redis واقعی برای اینکه ثابت کنم constraintها و اسکریپت Lua واقعاً کار می‌کنند، و E2E که کل برنامه را با همان پیکربندی production بالا می‌آورد و از طریق HTTP تست می‌کند. همه‌ی این‌ها در CI هم اجرا می‌شوند.
>
> چیزهایی هم هست که عمداً در محدوده نیاوردم یا هنوز ندارم: refresh token، ویرایش و حذف، لایک و فالو، آپلود رسانه، و صفحه‌بندی cursor. اگر بخواهم پروژه را ادامه بدهم، اولویتم refresh token و rate limit برای login است.»
