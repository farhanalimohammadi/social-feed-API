# ۱۱ - تصمیم‌های معماری و trade-offها

این سند تصمیم‌های معماری پیاده‌سازی‌شده را به سبک ADR (Architecture Decision Record) ثبت می‌کند. هر تصمیم در کد فعلی تأیید شده است. بخش «مسیر تکامل» فقط پیشنهاد است و **پیاده‌سازی نشده**.

---

## ADR-01: معماری ماژولار مبتنی بر feature در NestJS

- **تصمیم:** هر دامنه یک ماژول NestJS مستقل در `src/modules/<feature>/` دارد. زیرساخت در `src/infrastructure/` قرار دارد و اجزای مشترک در `src/common/`.
- **زمینه:** پروژه چند دامنه‌ی مرتبط دارد (auth، posts، comments، users) که باید مرز روشنی داشته باشند.
- **رویکرد انتخابی:** ماژول به ازای feature با `imports` و `exports` صریح، و Controller و Service و DTO و select و mapper درون همان پوشه.
- **دلیل:** هم‌مکانی کد مرتبط، DI صریح و قابلیت تست.
- **مزایا:** مرز وابستگی‌ها در `*.module.ts` قابل مشاهده است. فقط `PostsService` و `CommentsService` export شده‌اند.
- **هزینه‌ها:** کمی boilerplate (ماژول‌های کوچک مثل `RateLimitModule`).
- **گزینه‌های ردشده:** ساختار لایه‌ای سراسری (`controllers/`، `services/`)، و Express خام.
- **مسیر تکامل:** جداسازی ماژول‌ها به پکیج‌های مستقل در صورت رشد.

## ADR-02: ESM و TypeScript سخت‌گیر

- **تصمیم:** `"type": "module"`، `module` و `moduleResolution` برابر `nodenext`، و `strict: true` به‌همراه `noImplicitOverride` و `noFallthroughCasesInSwitch`.
- **زمینه:** Node.js 22 و اکوسیستم مدرن به سمت ESM حرکت کرده‌اند.
- **دلیل:** هم‌خوانی با استاندارد ماژول‌های جاوااسکریپت و ایمنی نوع حداکثری.
- **مزایا:** خطاهای نوع زودتر کشف می‌شوند و بارگذاری ماژول‌ها رفتار استاندارد دارد.
- **هزینه‌ها:** importهای نسبی باید پسوند `.js` داشته باشند. برخی کتابخانه‌های CommonJS به `esModuleInterop` نیاز دارند (مثل `import * as bcrypt`).
- **گزینه‌های ردشده:** CommonJS.
- **مسیر تکامل:** -

## ADR-03: PostgreSQL به‌عنوان منبع حقیقت

- **تصمیم:** همه‌ی داده‌های ماندگار فقط در PostgreSQL ذخیره می‌شوند و یکپارچگی در خود پایگاه داده اجرا می‌شود.
- **زمینه:** داده‌ها رابطه‌ای‌اند و قواعد بین‌جدولی دارند (پاسخ فقط در همان پست).
- **رویکرد:** قیدهای `UNIQUE`، FK مرکب، `CHECK` و `RESTRICT`.
- **دلیل:** برنامه ممکن است باگ داشته باشد یا race در آن رخ دهد، اما قید پایگاه داده همیشه اجرا می‌شود.
- **مزایا:** دفاع دولایه (Service و پایگاه داده). تست Integration مستقیم روی قیدها وجود دارد.
- **هزینه‌ها:** قیدهای `CHECK` و indexهای جزئی فقط در SQL دستی وجود دارند و Prisma از آن‌ها آگاه نیست.
- **گزینه‌های ردشده:** پایگاه داده‌ی سندمحور، و اعتبارسنجی فقط در برنامه.
- **مسیر تکامل:** read replica برای خواندن (پیاده‌سازی نشده).

## ADR-04: Prisma 7 با `@prisma/adapter-pg`

- **تصمیم:** generator از نوع `prisma-client` با خروجی در `src/generated/prisma`، و اتصال از طریق `PrismaPg`.
- **زمینه:** در Prisma 7 آدرس اتصال از schema به فایل config منتقل شده است.
- **رویکرد:** `prisma7.config.ts` برای CLI و `PrismaPg({ connectionString })` در runtime.
- **دلیل:** API تایپ‌شده، migrationهای مدیریت‌شده و انواع مشتق‌شده از select.
- **مزایا:** `Prisma.XGetPayload<{ select }>` نوع دقیق ردیف را تولید می‌کند و mapperها در زمان کامپایل بررسی می‌شوند.
- **هزینه‌ها:** کلاینت تولیدشده commit نمی‌شود و باید `prisma:generate` اجرا شود. همه‌ی دستورهای CLI به `--config` نیاز دارند. `$connect()` در startup اتصال واقعی را تضمین نمی‌کند (مشاهده‌شده).
- **گزینه‌های ردشده:** TypeORM، Drizzle، و SQL خام با `pg`.
- **مسیر تکامل:** -

## ADR-05: نبود لایه‌ی Repository

- **تصمیم:** Serviceها مستقیماً از `PrismaService` استفاده می‌کنند.
- **زمینه:** `PrismaClient` خودش یک API سطح بالا و تایپ‌شده است.
- **دلیل:** Repository نازک فقط متدهای Prisma را تکرار می‌کرد. selectهای نام‌دار و mapperها جداسازی لازم را فراهم می‌کنند.
- **مزایا:** کد کمتر و ردیابی ساده‌تر. Serviceها با mock ساده‌ی شیء Prisma تست می‌شوند.
- **هزینه‌ها:** وابستگی Serviceها به API خاص Prisma. تعویض ORM پرهزینه است.
- **گزینه‌های ردشده:** الگوی Repository یا DAO.
- **مسیر تکامل:** اگر queryها پیچیده یا مشترک شوند، استخراج query objectها.

## ADR-06: select صریح در Prisma

- **تصمیم:** هر query خواندنی یک شیء select نام‌دار با `satisfies Prisma.XSelect` دارد.
- **زمینه:** جدول `users` شامل `password_hash` است.
- **دلیل:** حداقل‌سازی داده‌ی واکشی‌شده و جلوگیری از نشت تصادفی.
- **مزایا:** `passwordHash` فقط یک‌جا و صریحاً select می‌شود (`login`). ایمیل در پاسخ‌های عمومی وجود ندارد. انواع ردیف از select مشتق می‌شوند.
- **هزینه‌ها:** هر فیلد جدید باید آگاهانه به select اضافه شود.
- **گزینه‌های ردشده:** واکشی کل مدل و حذف فیلد در serializer.
- **مسیر تکامل:** -

## ADR-07: احراز هویت فقط با access token از نوع JWT

- **تصمیم:** فقط access token با payload `{ sub }`، عمر قابل پیکربندی و الگوریتم `HS256`.
- **زمینه:** محدوده‌ی پروژه به جریان کامل مدیریت session نیاز نداشت.
- **دلیل:** سادگی و stateless بودن.
- **مزایا:** پیاده‌سازی کوچک و قابل‌فهم و بدون نیاز به ذخیره‌سازی session.
- **هزینه‌ها:** لغو تک‌توکن، logout و چرخش توکن وجود ندارد.
- **گزینه‌های ردشده:** session مبتنی بر cookie، و جفت refresh و access.
- **مسیر تکامل:** refresh token با چرخش و ذخیره در پایگاه داده (پیاده‌سازی نشده).

## ADR-08: جست‌وجوی کاربر در پایگاه داده در `JwtStrategy`

- **تصمیم:** در `validate` شکل `sub` (UUID نسخه‌ی ۴) بررسی و کاربر با `publicUserSelect` خوانده می‌شود.
- **زمینه:** JWT به‌تنهایی نمی‌داند کاربر هنوز وجود دارد یا نه.
- **دلیل:** کاربر حذف‌شده باید فوراً دسترسی‌اش را از دست بدهد و `request.user` باید داده‌ی تازه داشته باشد.
- **مزایا:** حذف کاربر بلافاصله اثر دارد. `request.user` شامل `username` و `email` به‌روز است.
- **هزینه‌ها:** یک query با کلید اصلی در هر درخواست محافظت‌شده. API فعلی endpoint حذف کاربر ندارد.
- **گزینه‌های ردشده:** اعتماد کامل به claimهای توکن.
- **مسیر تکامل:** cache کوتاه‌مدت کاربر یا نسخه‌ی توکن در جدول `users` (پیاده‌سازی نشده).

## ADR-09: bcrypt برای رمز عبور

- **تصمیم:** bcrypt با `BCRYPT_COST = 10`، محدودیت ۸ تا ۷۲ بایت و dummy hash برای ایمیل ناموجود.
- **زمینه:** محدودیت ۷۲ بایتی bcrypt و خطر user enumeration.
- **دلیل:** الگوریتم شناخته‌شده و کتابخانه‌ی پایدار.
- **مزایا:** پیام و هزینه‌ی زمانی نزدیک به هم در دو حالت شکست ورود.
- **هزینه‌ها:** cost ثابت در کد. ثبت‌نام با `409` وجود ایمیل را آشکار می‌کند.
- **گزینه‌های ردشده:** Argon2 و scrypt.
- **مسیر تکامل:** قابل پیکربندی کردن cost، و rate limit برای login (پیاده‌سازی نشده).

## ADR-10: cache-aside در Redis برای فید

- **تصمیم:** فقط `GET /api/v1/posts` با الگوی cache-aside و TTL قابل پیکربندی cache می‌شود.
- **زمینه:** فید عمومی پرخواندن‌ترین endpoint است و هر آیتم آن شامل join و شمارش است.
- **دلیل:** ساده‌ترین الگو که Redis را اختیاری نگه می‌دارد.
- **مزایا:** HIT بدون query به پایگاه داده. MISS و خرابی Redis به پایگاه داده برمی‌گردند. payload همان DTO نهایی است و با codec اعتبارسنجی می‌شود.
- **هزینه‌ها:** احتمال کهنگی محدود. فضای کلید به ازای هر ترکیب `page` و `limit`.
- **گزینه‌های ردشده:** write-through، cache کامل جدول، و cache در حافظه‌ی process (در چند instance ناسازگار می‌شد).
- **مسیر تکامل:** cache برای `GET /posts/:id` یا پروفایل (پیاده‌سازی نشده).

## ADR-11: invalidation مبتنی بر generation

- **تصمیم:** با هر پست یا کامنت جدید، `INCR posts:feed:v1:generation` اجرا می‌شود. کلید هر صفحه شامل generation است.
- **زمینه:** یک پست جدید همه‌ی صفحات فید را جابه‌جا می‌کند و حذف تک‌تک کلیدها به `KEYS` یا `SCAN` نیاز داشت.
- **دلیل:** invalidation اتمیک با هزینه‌ی O(1).
- **مزایا:** نیازی به `KEYS` نیست. race بین خواننده و نویسنده با نوشتن زیر generation قدیمی بی‌خطر می‌شود.
- **هزینه‌ها:** کلیدهای قدیمی تا پایان TTL حافظه مصرف می‌کنند. هر نوشتنی کل فید را باطل می‌کند، حتی اگر فقط صفحه‌ی اول تغییر کرده باشد.
- **گزینه‌های ردشده:** حذف با الگو، و pub/sub.
- **مسیر تکامل:** -

## ADR-12: طراحی fail-open برای Redis

- **تصمیم:** `RedisService` همه‌ی خطاها را به `null` تبدیل می‌کند. cache به پایگاه داده برمی‌گردد و rate limit درخواست را می‌پذیرد.
- **زمینه:** Redis برای درستی داده ضروری نیست.
- **دلیل:** خرابی یک زیرساخت جانبی نباید قابلیت اصلی را از کار بیندازد.
- **مزایا:** برنامه بدون Redis بالا می‌آید و کار می‌کند (مشاهده‌شده). timeoutهای کوتاه و `enableOfflineQueue: false` از معطلی جلوگیری می‌کنند.
- **هزینه‌ها:** در زمان خرابی Redis، حفاظت ضداسپم وجود ندارد و بار پایگاه داده افزایش می‌یابد.
- **گزینه‌های ردشده:** fail-closed (رد ساخت پست هنگام خرابی Redis).
- **مسیر تکامل:** rate limit پشتیبان در حافظه‌ی process، و metric برای حالت degraded (پیاده‌سازی نشده).

## ADR-13: rate limit پنجره‌ی ثابت با Lua

- **تصمیم:** کلید به ازای کاربر و پنجره‌ی هم‌تراز با epoch، و اسکریپت Lua شامل `INCR` و در صورت `count == 1`، اجرای `EXPIRE`.
- **زمینه:** شمارش باید در چند درخواست هم‌زمان و چند instance دقیق باشد.
- **دلیل:** اتمیک بودن در Redis، هزینه‌ی O(1) و یک round-trip.
- **مزایا:** تست هم‌زمانی با ۲۵ درخواست موازی دقیقاً ۱۰ پذیرش می‌دهد. TTL تضمین‌شده و بدون کلید یتیم.
- **هزینه‌ها:** انفجار تا `2 × limit` در مرز پنجره. درخواست‌هایی که بعداً در validation رد شوند هم سهمیه مصرف می‌کنند.
- **گزینه‌های ردشده:** sliding window log، token bucket، و `INCR` و `EXPIRE` جداگانه.
- **مسیر تکامل:** sliding window، و rate limit برای login و کامنت (پیاده‌سازی نشده).

## ADR-14: صفحه‌بندی offset

- **تصمیم:** `page` و `limit` با `skip` و `take`، و `meta` شامل `totalItems` و `totalPages`.
- **زمینه:** کلاینت‌ها به شماره‌ی صفحه و تعداد کل نیاز دارند.
- **دلیل:** سادگی و هم‌خوانی با cache به ازای هر صفحه.
- **مزایا:** پرش مستقیم به هر صفحه. ترتیب قطعی با `id` به‌عنوان tie-breaker.
- **هزینه‌ها:** هزینه‌ی `OFFSET` در صفحات عمیق. جابه‌جایی آیتم‌ها بین صفحات هنگام درج هم‌زمان. `count` در هر درخواست. `count` و `findMany` در یک تراکنش نیستند.
- **گزینه‌های ردشده:** صفحه‌بندی cursor یا keyset.
- **مسیر تکامل:** cursor با `(createdAt, id)`. indexهای موجود از قبل با این ترتیب هم‌خوان‌اند (پیاده‌سازی نشده).

## ADR-15: خواندن پاسخ‌ها فقط در یک سطح

- **تصمیم:** API لیست کامنت‌های سطح اول و لیست پاسخ‌های **مستقیم** یک کامنت را جداگانه ارائه می‌کند. درخت بازگشتی برگردانده نمی‌شود.
- **زمینه:** بارگذاری درخت کامل کامنت‌ها هزینه‌ی نامحدود دارد.
- **دلیل:** هر درخواست هزینه‌ی محدود و قابل صفحه‌بندی دارد.
- **مزایا:** queryهای ساده با indexهای جزئی. `totalReplies` به کلاینت می‌گوید آیا بارگذاری بیشتر لازم است.
- **هزینه‌ها:** کلاینت برای هر سطح یک درخواست جدا می‌زند. **عمق ایجاد محدود نشده است**، یعنی پاسخ به پاسخ هم پذیرفته می‌شود.
- **گزینه‌های ردشده:** درخت بازگشتی با CTE، و materialized path.
- **مسیر تکامل:** محدودیت عمق در Service (پیاده‌سازی نشده).

## ADR-16: ترکیب محدود فعالیت‌های اخیر

- **تصمیم:** پروفایل حداکثر ۵ پست و ۵ کامنت اخیر را موازی می‌خواند، در حافظه ترکیب و مرتب می‌کند و ۵ مورد اول را برمی‌گرداند. تاریخچه‌ی کامل در endpointهای جداگانه‌ی `/posts` و `/comments` با صفحه‌بندی ارائه می‌شود.
- **زمینه:** صفحه‌بندی روی اجتماع (union) دو جدول پیچیده است.
- **دلیل:** هزینه‌ی ثابت برای پروفایل (حداکثر ۱۰ ردیف) و صفحه‌بندی ساده برای تاریخچه.
- **مزایا:** از نظر منطقی، برای به دست آوردن ۵ مورد جدیدِ ترکیبی، خواندن ۵ مورد جدید از هر منبع کافی است، چون هیچ آیتمی خارج از ۵ مورد اول منبع خودش نمی‌تواند در ۵ مورد اول ترکیب باشد. Unit Test مرتب‌سازی و tie-break را پوشش می‌دهد.
- **هزینه‌ها:** تاریخچه‌ی ترکیبی صفحه‌بندی‌شده وجود ندارد. سه query پروفایل حتی برای کاربر ناموجود اجرا می‌شوند.
- **گزینه‌های ردشده:** `UNION ALL` در SQL خام با صفحه‌بندی.
- **مسیر تکامل:** -

## ADR-17: foreign key مرکب برای پاسخ‌ها

- **تصمیم:** `(parent_comment_id, post_id) → comments(id, post_id)` به‌همراه `@@unique([id, postId])`.
- **زمینه:** FK ساده جلوی پاسخ بین‌پستی را نمی‌گیرد.
- **دلیل:** تضمین قاعده در خود پایگاه داده، مستقل از برنامه و race.
- **مزایا:** تست Integration اثبات می‌کند که پاسخ بین‌پستی رد می‌شود.
- **هزینه‌ها:** یک index یکتای اضافه روی `(id, post_id)`. خطای FK به کد HTTP خاصی نگاشت نشده است (در صورت وقوع `500`). در حالت عادی Service پیش از آن `400` برمی‌گرداند.
- **گزینه‌های ردشده:** trigger، و بررسی فقط در برنامه.
- **مسیر تکامل:** نگاشت خطای `P2003` به `400` یا `409` (پیاده‌سازی نشده).

## ADR-18: `onDelete: Restrict`

- **تصمیم:** همه‌ی روابط `RESTRICT` هستند.
- **زمینه:** حذف آبشاری می‌تواند بی‌صدا حجم زیادی تاریخچه را پاک کند.
- **دلیل:** حذف باید آگاهانه و صریح باشد.
- **مزایا:** تست Integration حذف کاربری را که پست دارد رد می‌کند.
- **هزینه‌ها:** پیاده‌سازی حذف در آینده باید ترتیب حذف یا soft delete را مدیریت کند.
- **گزینه‌های ردشده:** `CASCADE` و `SET NULL`.
- **مسیر تکامل:** soft delete (پیاده‌سازی نشده).

## ADR-19: تفکیک تست به Unit، Integration و E2E

- **تصمیم:** سه پیکربندی Vitest و سه اسکریپت جداگانه.
- **زمینه:** بعضی ویژگی‌ها فقط با زیرساخت واقعی قابل اثبات‌اند (FK و Lua).
- **دلیل:** بازخورد سریع از Unit و اطمینان واقعی از Integration و E2E.
- **مزایا:** Unit بدون Docker اجرا می‌شود. `fileParallelism: false` از تداخل جلوگیری می‌کند. E2E از `configureApp` استفاده می‌کند.
- **هزینه‌ها:** Integration و E2E به PostgreSQL، Redis و migration نیاز دارند. E2E پایگاه داده را خالی نمی‌کند و به داده‌ی یکتا تکیه دارد.
- **گزینه‌های ردشده:** فقط E2E، یا فقط Unit با mock.
- **مسیر تکامل:** گزارش coverage (پیاده‌سازی نشده).

## ADR-20: Docker Compose با profile جداگانه برای برنامه

- **تصمیم:** Compose به‌طور پیش‌فرض فقط PostgreSQL و Redis را اجرا می‌کند. سرویس‌های `migrate` و `app` (از `Dockerfile` چندمرحله‌ای) در profile `app` هستند.
- **زمینه:** چرخه‌ی توسعه با `nest start --watch` روی میزبان سریع‌تر است، اما صورت تسک راه‌اندازی آسان با Docker Compose را می‌خواهد.
- **دلیل:** profile هر دو نیاز را بدون تغییر رفتار `docker compose up -d` برآورده می‌کند. migration در سرویس یک‌بارمصرف جدا اجرا می‌شود تا image نهایی به Prisma CLI (وابستگی dev) نیاز نداشته باشد.
- **مزایا:** پورت‌های غیراستاندارد از تداخل جلوگیری می‌کنند. healthcheck و AOF دارد. image نهایی فقط وابستگی‌های production را دارد و با کاربر غیر root اجرا می‌شود.
- **هزینه‌ها:** برای اجرای کامل باید `--profile app` را به یاد داشت. در حالت توسعه، نسخه‌ی Node میزبان باید با `.nvmrc` هم‌خوان باشد.
- **گزینه‌های ردشده:** سرویس `app` بدون profile (تداخل با `npm run start:dev`)، و اجرای migration داخل entrypoint برنامه.

## ADR-21: طراحی health endpoint

- **تصمیم:** liveness (`/health`) بدون وابستگی، و readiness (`/health/ready`) فقط با PostgreSQL و timeout برابر ۱۵۰۰ میلی‌ثانیه.
- **زمینه:** orchestratorها بین «زنده بودن process» و «آمادگی سرویس‌دهی» تمایز قائل می‌شوند.
- **دلیل:** خرابی پایگاه داده نباید باعث restart بی‌مورد process شود. Redis اختیاری است و نباید readiness را تحت تأثیر قرار دهد.
- **مزایا:** رفتار هر دو endpoint در E2E تست شده است.
- **هزینه‌ها:** پاسخ `503` به دلیل `AllExceptionsFilter` جزئیات Terminus را ندارد (مشاهده‌شده).
- **گزینه‌های ردشده:** یک endpoint واحد که همه‌ی وابستگی‌ها را بررسی کند.
- **مسیر تکامل:** استثنا کردن پاسخ Terminus در فیلتر، و گزارش وضعیت Redis به‌صورت اطلاعاتی (پیاده‌سازی نشده).

## بهبودهای آینده

**همه‌ی موارد زیر در کد فعلی پیاده‌سازی نشده‌اند.**

| مورد | توضیح |
|---|---|
| Refresh token | جفت access و refresh با چرخش و امکان لغو |
| OAuth | ورود با سرویس‌های خارجی |
| RBAC | نقش‌هایی مثل admin و moderator |
| Moderation | گزارش و پنهان‌سازی محتوا |
| ویرایش و حذف | برای پست، کامنت و حساب کاربری (با در نظر گرفتن `RESTRICT`) |
| لایک، فالو و نوتیفیکیشن | قابلیت‌های اجتماعی |
| ذخیره‌سازی رسانه | آپلود و object storage برای `image` و `video` |
| صفحه‌بندی cursor | بر اساس `(createdAt, id)` |
| rate limit با sliding window | رفع انفجار مرز پنجره |
| rate limit برای login، register و کامنت | حفاظت در برابر brute force و اسپم |
| قفل توزیع‌شده | در صورت نیاز به جلوگیری از cache stampede |
| Metrics و tracing | مثلاً شمارش حالت `degraded` و HIT/MISS |
| Swagger / OpenAPI | مستندات ماشین‌خوان API |
